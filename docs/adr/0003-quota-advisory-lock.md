# ADR 0003 — 회차당 구매 한도는 어드바이저리 락으로 지킨다

- 상태: 채택
- 날짜: 2026-09-09
- 관련: 설계 문서: 좌석 선점, `app/infra/db/queries.py`(`lock_user_quota`)

## 맥락

§5.2 의 선점 쿼리는 단일 CTE 로 "요청 좌석 전량 확보"와 "회차당 4매 한도"를
함께 판정하도록 설계했다. 앞의 것은 실제로 지켜지지만, **뒤의 것은 새는 것을
테스트로 확인했다.**

한 유저가 서로 다른 좌석 12석에 1석씩 동시 요청 →
**성공 7건** (한도는 4매).

## 원인

두 조건의 성격이 다르다.

- **좌석 전량 확보**는 특정 행들에 대한 조건이다. `FOR UPDATE` 가 그 행을 잠그므로
  같은 좌석을 노리는 요청들은 서로 직렬화된다. 이게 `test_single_seat_contention`
  과 `test_cross_seat_deadlock` 이 통과하는 이유다.
- **구매 한도**는 "이 유저가 이 회차에 몇 석 갖고 있나"라는 **술어(predicate)** 다.
  서로 다른 좌석을 노리는 동시 요청들은 공유하는 행이 없으므로 아무것도 잠그지
  않고, READ COMMITTED 에서 각자 `owned = 0` 을 읽는다. 전형적인 write skew 다.

핵심은 **셀 행이 아예 없을 수도 있는 조건은 행 잠금으로 지킬 수 없다**는 것이다
(phantom). 유저가 아직 아무것도 안 잡은 상태에서 12개 요청이 동시에 오면
잠글 대상 자체가 존재하지 않는다.

## 검토한 안

| 안 | 판정 |
|---|---|
| `SELECT ... FOR UPDATE` 로 기존 hold 잠그기 | **기각.** 행이 0개일 수 있어 phantom 을 막지 못한다 |
| SERIALIZABLE 격리 수준 | **기각.** 정확하지만 좌석 경합 경로 전체에 직렬화 실패 재시도 루프가 붙는다. 오픈런 경로에 넣을 비용이 아니다 |
| `users` 행을 `FOR UPDATE` 로 잠그기 | 동작하지만 범위가 과도하다. 한 유저의 서로 다른 회차 예매까지 직렬화된다 |
| **(회차, 사용자) 어드바이저리 락** | **채택** |

## 결정

`hold_seats` 직전, 같은 트랜잭션에서

```sql
SELECT pg_advisory_xact_lock(hashtext('curtain.hold:' || schedule_id || ':' || user_id)::bigint)
```

- 직렬화 범위가 **(회차, 사용자) 하나**다. 좌석 경합 경로에는 영향이 없고,
  다른 유저들끼리는 여전히 완전 병렬이다.
- `_xact_` 이므로 커밋·롤백 시 자동 해제된다. 명시적 해제를 잊을 수 없다.
- 해시 충돌은 관계없는 두 쌍이 불필요하게 직렬화되는 것일 뿐, 오답이 아니다.

## 왜 별도 문장인가

한 문장 안의 non-data-modifying CTE 는 실행 순서가 보장되지 않는다. 락 CTE 를
쿼리에 끼워 넣어도 `owned` 절보다 먼저 평가된다는 보장이 없다. "락이 먼저"를
SQL 로 표현할 방법이 없으므로 문장을 분리했다.

선점이 2왕복이 된 것은 이 결정의 대가다. 다만 §5.2 가 단일 문장이어야 했던
이유(좌석에 대한 read-then-write 틈 제거)는 그대로 지켜진다 — 좌석 판정은
여전히 CTE 안에서 한 번에 끝난다.

## 남은 것

한도 검사는 이제 정확하지만, 이것은 **남용 방지 정책**이지 정합성 불변식이
아니다. 오버부킹은 `uq_schedule_seat` 과 `order_items.schedule_seat_id UNIQUE`
가 구조적으로 막는다 — 그 방어선은 이 락과 무관하게 계속 유효하다.
매크로·부정 예매 탐지는 여전히 §11 에서 미룬 항목이다.
